# 招聘办理 · 需求文档（按环节种类）

> 适用页面：`hr/process-audit/process-audit.html`（招聘办理）
> 组织方式：按流程节点「环节种类」分四章展开——**资格审查型 / 考试型 / 常规审核页面型 / 录用环节型**。每一类先给类型级基线（状态签、列表列、操作形态），再逐节点写明内容、字段、操作与影响因素；最后汇总跨环节的通用影响因素与交互规则。

## 0. 页面总览（四部分组成）

| 组成部分 | 说明 |
|---|---|
| ① 顶部页签 | 「待我办理」（显示当前登录人有权限办理的候选人总数）/「我已办理」（本人已处理记录）。 |
| ② 左侧三级树 | 招聘计划 → 招聘种类 → 流程节点（叶子）。点击叶子加载该节点下、当前页签的候选人列表。详见《招聘办理-左侧树结构.md》。 |
| ③ 右侧主区 | 查询区 + 批量操作区 + 候选人列表。列表列与批量按钮随「当前选中节点 + 子状态」动态切换。 |
| ④ 候选人详情抽屉 | 基本信息 / 学历学位 / 工作简历 / 获奖 / 职务资格 / 科研 / 附件 + 类型专属区块 + 办理轨迹；承载单条操作。 |

**角色与权限**：人事处管理员、学院招聘负责人共同使用本页。不同节点由不同角色办理——资格审查（学院）、学院面试、名单确认（人事处）等由学院/人事处分角色办理；校级审核、校级面试、招聘录用等由人事处办理。权限不足时不显示对应批量/单条操作。

**前置条件**：① 招聘计划已审核通过并发布；② 岗位已发布且处于报名/招聘中；③ 候选人已完成报名并进入当前流程节点。

**后置条件**：办理结果更新候选人当前节点状态——通过则进入下一节点、退回则回退上一/指定节点、不通过/放弃/已录用为终态；办理轨迹完整留痕，结果同步至招聘网站公示与后续环节。

## 1. 环节种类的划分逻辑（总览）

第三级叶子节点名称很多，但按「**状态签序列 + 操作形态 + 列表列形态**」可归并为 4 种典型类型。类型决定了右侧列表的**状态列、批量操作栏、单条操作菜单、详情专属区块**。

| 类型 | 代表节点 | 状态签形态 | 批量操作基线 | 单条操作基线 | 列表差异列 |
|---|---|---|---|---|---|
| **① 资格审查型** | 资格审查 / 资格审查（学院）/ 资格复审 | 单一签 `待审核` | 批量通过 / 批量退回(须原因) / 批量不通过 | 符合 / 退回 / 不符合（或「通过并下一位」） | 显式「AI 预审」「AI 建议」列 |
| **② 考试型** | 笔试 / 面试 / 学院面试 / 校级面试 / 综合素质考察 | `待确认参加 → 待发准考证 → 待录成绩`（综合素质考察为 `待上传成绩 → 待审核`） | 确认参加 / 确认不参加、发放准考证、导入成绩、通过/不通过 | 确认参加 / 确认不参加、发放准考证、录入、通过/不通过 | 显式「确认状态」「准考证号」「成绩」「排名」列 |
| **③ 常规审核页面型** | 校级审核 / 委员会评议 / 名单确认（人事处）/ 体检 / 心理测试 | `待审核`（审核类）；或 `待确认参加 → 待登记结果`（结果登记子类） | 通过 / 不通过 / 退回（体检类为登记合格/不合格） | 退回 / 不通过 / 通过（或「通过并下一位」） | 显式「体检结果」「调档函」「录用状态」等（录用前序节点） |
| **④ 录用环节型** | 招聘录用 | `待录用确认 → 已录用`（终态） | 录用确认、生成调档函、汇总表导出、公示发布 | 确认体检结果 / 生成调档函 / 录用确认 | 显式「体检结果」「调档函」「档案保管单位」「录用状态」列 |

> **类型归类依据（原型 `typeOfStage` 现状，标注供实现对齐）**：原型内部把 `名单确认（人事处）`、`部门初试` 暂归「资格审查」类，`委员会评议`、`校级面试` 暂归「考试」类。本需求文档按**用户指定的 4 类**组织（名单确认归③、委员会评议归③），实现时需将原型 `typeOfStage` 与字段池 `FIELD_DEFS[].types` 一并调整为一致，否则「名单确认」「委员会评议」的字段配置池与操作形态会与本文档不符。

## 2. 类型一 · 资格审查型

### 2.0 类型基线
- **形态**：对候选人资格材料做准入判断，结论三元（通过 / 退回 / 不通过）。无准考证、无成绩，纯材料审核。
- **状态签**：`待审核`（单一）。
- **列表差异列**：`AI 预审`（绿色「符合」/红色「不符合」标签，列头可排序）、`AI 建议`（命中/未命中岗位要求的说明文本）。两列仅资格审查类节点显示。
- **批量操作**：批量符合（通过）/ 批量退回（须填退回原因，可选退回目标环节）/ 批量不符合（不通过，须填原因）。
- **单条操作**：符合 / 退回 / 不符合（或「通过并下一位」）。
- **详情专属区块**：顶部「AI 综合建议」概述（符合/不符合 + 原因列表）。

### 2.1 资格审查
- **定位**：出现在「先笔后面」「先面后笔」种类的流程链首位（位于资格审查（学院）之前）；属校级/人事处层面统一资格把关。
- **内容**：基于报名表与附件，判断学历、年龄、岗位要求等硬性条件是否满足。
- **列表列**：复选框、姓名、联系方式、AI 预审、AI 建议、应聘岗位、毕业院校、学历、操作（详情）。
- **批量/单条操作**：见 2.0 基线（批量通过/批量退回/批量不通过）。
- **影响因素**：
  - **出现条件**：由招聘种类决定——`先笔后面`/`先面后笔` 含「资格审查」节点；`选聘` 下该环节以「资格审查（学院）」名称呈现（见 §7.3 重映射）。
  - **AI 预审驱动**：`AI 预审`/`AI 建议` 列来自系统对岗位要求的自动匹配，仅作辅助；最终结论须人工确认，AI 命中不自动通过。
  - **退回目标**：退回须指定回退环节（默认回报名或上一环节），原因必填并留痕。
  - **状态已变化**：记录若已被他人审核或状态不再为 `待审核`，本操作终止并提示最新状态，不覆盖他人结论。

### 2.2 资格审查（学院）
- **定位**：「选聘」种类流程链首位节点；也可由学院在人事处统审前置阶段办理，是截图示例中的当前节点。
- **内容**：学院对本院应聘者的资格初筛，结论同样三元；退回与不符合均须填原因。
- **列表列**：同 2.1（含 AI 预审/AI 建议）。
- **批量/单条操作**：批量符合 / 批量退回 / 批量不符合（批量）；单条为 符合 / 退回 / 不符合。
- **影响因素**：
  - **角色绑定**：由学院招聘负责人办理；人事处管理员视权限可见或代办理。
  - **与 2.1 的差异**：仅在「选聘」种类下以本名称出现；其余种类下同名环节为「资格审查」。
  - **数据同源**：AI 预审结果与 2.1 共用同一套岗位要求匹配逻辑，不因节点更名而变。

### 2.3 资格复审
- **定位**：出现在「先笔后面」种类、笔试/面试之后的复核环节（流程链：`…笔试 → 面试 → 资格复审 → 校级审核 → 招聘录用`）；对前期资格结论做二次确认。
- **内容**：在考试完成后，对资格材料与考试资格做复审，防止「考试通过但资格不符」的情况。
- **列表列**：同 2.1（含 AI 预审/AI 建议）。
- **批量/单条操作**：批量通过 / 退回 / 不通过（批量）；单条 通过 / 退回 / 不通过。
- **影响因素**：
  - **出现位置依赖**：仅在含笔试/面试的种类（先笔后面）中出现，且位于考试环节之后；选聘、先面后笔 不含本节点。
  - **前序强约束**：必须在面试完成且候选人未进入终态时才可办理；若前序考试已「不通过/放弃」，本节点不出现该候选人。
  - **退回语义**：复审退回可回退至考试环节或学院，需明确退回目标。

## 3. 类型二 · 考试型

### 3.0 类型基线
- **形态**：含「准考证 + 成绩」的考核环节，成绩驱动晋级；同一形态复用于多场考试（笔试/面试/学院面试/校级面试）。
- **状态签**：`待确认参加 → 待发准考证 → 待录成绩`。综合素质考察为 `待上传成绩 → 待审核`。
- **列表差异列**：显式「确认状态」「准考证号」「成绩」「排名」等结构性状态列（由系统按子状态自动呈现，不属于可配置数据字段）。
- **批量操作**：确认参加 / 确认不参加、发放准考证、导入成绩（或录入成绩）、通过/不通过。
- **单条操作**：确认参加 / 确认不参加、发放准考证、录入、通过/不通过、通过并下一位（面试结果确认）。
- **详情专属区块**：「考试情况」汇总（校级审核节点下显示资格审查/笔试/面试/体检/心理测试/综合意见各结论）。

### 3.1 笔试
- **定位**：「先笔后面」「先面后笔」种类的笔试环节；先面后笔中为面试后的第二轮笔试。
- **状态签与操作阶段**：
  - `待确认参加`：批量 确认参加/确认不参加；单条同。
  - `待发准考证`：批量 发放准考证（及「准考证」查看）；单条 发放准考证。
  - `待录成绩`：批量 导入成绩；单条 通过/不通过（成绩已录入后做晋级判断）。
- **列表列**：复选框、姓名、联系方式、应聘岗位、确认状态、准考证号、成绩、排名、操作（详情）。
- **影响因素**：
  - **确认不参加即终止**：确认不参加 → 该候选人退出本环节，不再发准考证、不录成绩（视为不晋级）。
  - **准考证唯一匹配**：准考证号由系统生成（如 `2026xxxxx`），发放后状态转 `已发未下载/已下载`；成绩导入按准考证号唯一匹配人员，匹配失败行明确提示并可下载失败清单。
  - **成绩驱动晋级**：成绩录入后进入 `待确认结果`（合并成绩视图），由人工「通过并下一位/不通过」决定晋级面试或终止。
  - **出现条件**：由招聘种类决定顺序——先笔后面「笔试」在面试前，先面后笔「笔试」在面试后。

### 3.2 面试
- **定位**：「先笔后面」「先面后笔」的面试环节；先笔后面中笔试之后，先面后笔中笔试之前。
- **状态签与操作**：同 3.1（待确认参加→待发准考证→待录成绩→待确认结果）。
- **列表列**：同 3.1。
- **影响因素**：
  - **顺序依赖**：与 3.1 笔试的相对顺序由招聘种类决定（先笔后面：笔试→面试；先面后笔：面试→笔试）。
  - **成绩合并视图**：`待录成绩` 子状态下，列表同时聚合「已发准考证且已发」与「待确认结果」两类人员，便于一次性完成面试打分与晋级判断。
  - **确认不参加 / 不通过**：任一均终止该候选人本环节流转。

### 3.3 学院面试
- **定位**：「选聘」种类的第三节点（资格审查（学院）→ 名单确认（人事处）→ 学院面试 → 委员会评议 → 校级面试 → 校级审核 → 招聘录用）。
- **状态签与操作**：同 3.1 三阶段；`待录成绩` 单条动作为「录入」（区别于笔试/面试的「导入成绩」）。
- **列表列**：同 3.1（含确认状态/准考证号/成绩/排名）。
- **影响因素**：
  - **名称映射**：选聘下「学院面试」对应通用流程的「综合素质考察」节点（见 §7.3 重映射），但保留面试形态的操作（录入成绩）。
  - **成绩录入方式**：单条「录入」为逐人填写，区别于批量「导入成绩」；两者最终都写入成绩字段并触发晋级判断。
  - **子状态归一**：进入学院面试的候选人若子状态异常，原型统一重置为 `待确认参加`，确保从确认参加重新流转。

### 3.4 校级面试
- **定位**：「选聘」种类的第五节点（委员会评议之后）；属人事处校级层面面试。
- **状态签与操作**：同 3.3（待确认参加→待发准考证→待录成绩；单条「录入」）。
- **列表列**：同 3.1。
- **影响因素**：
  - **前序依赖**：必须在「委员会评议」通过后进入；委员会评议未通过者不在本节点列表。
  - **名称映射**：选聘下「校级面试」对应通用流程的「资格复审」节点（见 §7.3），但保留面试形态。
  - **晋级终态前最后考试环节**：通过后进入校级审核，再至招聘录用。

### 3.5 综合素质考察
- **定位**：「先笔后面」「先面后笔」种类中位于资格审查之后、考试之前的考察环节（流程链：`资格审查 → 综合素质考察 → 笔试/面试 → …`）。
- **状态签**：`待上传成绩 → 待审核`（区别于其他考试节点的三阶段）。
- **列表列**：复选框、姓名、联系方式、应聘岗位、确认状态、成绩、操作（详情）。
- **批量/单条操作**：批量 上传综合素质考察成绩；单条 通过/不通过（待审核时）、退回/不通过/通过（待审核）。
- **影响因素**：
  - **形态差异**：无准考证发放阶段，直接进入成绩上传与审核；成绩上传后由人工审核通过/不通过。
  - **顺序定位**：固定位于资格审查之后、首场考试之前；是考试型中唯一不绑定准考证的子类。
  - **选聘映射**：选聘下以「学院面试」名称呈现（§7.3），但保留考察成绩录入逻辑。

## 4. 类型三 · 常规审核页面型

### 4.0 类型基线
- **形态**：通用审核页，录入审核结论 + 意见，可退回上一环节；体检/心理测试为其「结果登记」子类（无审核意见，仅登记合格/不合格）。
- **状态签**：`待审核`（审核类）；或 `待确认参加 → 待登记结果`（结果登记子类）。
- **列表差异列**：审核类显示结论相关列；结果登记子类显示「体检结果」「调档函」「档案保管单位」「录用状态」等（临近录用前序节点时）。
- **批量操作**：通过 / 不通过 / 退回（审核类）；登记合格/不合格（体检/心理测试子类）。
- **单条操作**：退回 / 不通过 / 通过（或「通过并下一位」）。
- **详情专属区块**：「考试情况」汇总（校级审核节点）、「部门初试意见」（部门初试节点）。

### 4.1 校级审核
- **定位**：所有含考试环节种类的收口审核（先笔后面：资格复审后；先面后笔：笔试后；选聘：校级面试后）。
- **状态签**：`待审核`。
- **列表列**：复选框、姓名、联系方式、应聘岗位、操作（详情）；详情内「考试情况」区块汇总资格审查/笔试/面试/体检/心理测试/综合意见。
- **批量/单条操作**：批量 通过/不通过；单条 退回/不通过/通过并下一位。
- **影响因素**：
  - **综合审议**：承载对前面所有环节结论的综合判断，通常位于流程中后段；不绑定成绩，结论以意见文本为主。
  - **退回语义**：可退回至上一环节（如校级面试/资格复审）重走，须填原因。
  - **通过即拟录取**：通过后状态进入「拟录取待转录用」，衔接招聘录用。

### 4.2 委员会评议
- **定位**：「选聘」种类的第四节点（学院面试之后、校级面试之前）；由评议委员会对学院面试结果做评议。
- **状态签**：`待审核`。
- **列表列**：同 4.1。
- **批量/单条操作**：批量 通过/不通过；单条 通过/不通过（无退回，属终局性评议）。
- **影响因素**：
  - **位置绑定**：仅选聘种类存在，且必须在学院面试通过后进入。
  - **归类说明**：本文档归为③常规审核页面型（用户指定）；原型 `typeOfStage` 暂将其归「考试」类，实现时需调整字段池与操作形态一致（见 §1 注）。
  - **无退回**：评议为单向通过/不通过，不提供退回上一环节。

### 4.3 名单确认（人事处）
- **定位**：「选聘」种类的第二节点（资格审查（学院）之后、学院面试之前）；人事处对学院提交名单的确认。
- **状态签**：`待审核`。
- **列表列**：同 4.1。
- **批量/单条操作**：批量 通过/退回/不通过；单条 退回学院复核/不通过/确认通过。
- **影响因素**：
  - **角色绑定**：人事处办理；单条「退回学院复核」明确退回至学院层面重审。
  - **归类说明**：本文档归为③常规审核页面型；原型 `typeOfStage` 暂将其归「资格审查」类，实现时需统一（见 §1 注）。
  - **流程闸门**：确认通过后方可进入学院面试，是选聘流程中承上启下的关键确认点。

### 4.4 体检
- **定位**：常规审核页面型的「结果登记」子类；按招聘计划可安排在面试/校级审核之后。
- **状态签**：`待确认参加 → 待登记结果`。
- **列表列**：复选框、姓名、联系方式、应聘岗位、确认状态、操作（详情）；临近录用时列表附加「体检结果」「调档函」「档案保管单位」「录用状态」。
- **批量/单条操作**：`待确认参加` 确认参加/确认不参加；`待登记结果` 批量登记合格（批量 不合格/登记合格）。
- **影响因素**：
  - **结果登记形态**：不录审核意见，仅登记合格/不合格；不合格即终止（不录用）。
  - **⚠️ 接入缺口（原型现状）**：`体检` 已在 `STATUS_SEQUENCES`/`NODE_ACTIONS`/`DETAIL_ACTIONS` 中定义状态与操作，但**未出现在任何一种招聘种类的 `PROCESS_NODES_BY_TYPE` 序列中**。需求上体检为必办环节，实现时须将其加入对应种类的流程链（如校级审核之后、招聘录用之前），否则左侧树不会显示该节点。
  - **确认不参加**：退出本环节，视为放弃后续录用。

### 4.5 心理测试
- **定位**：与体检同属「结果登记」子类；考察候选人心理素质。
- **状态签**：`待确认参加 → 待登记结果`。
- **列表列/操作**：同 4.4。
- **影响因素**：
  - **同体检接入缺口**：已定义状态与操作，但**未接入 3 种招聘种类的流程链**，实现时需补齐。
  - **结果语义**：登记合格/不合格，不合格不终止流程（区别于体检，心理测试不合格通常仅作参考，是否影响录用由校级审核综合判断——需求待确认）。

## 5. 类型四 · 录用环节型

### 5.1 招聘录用
- **定位**：流程终点环节，生成录用结果并衔接调档、公示；所有招聘种类流程链的末节点。
- **状态签**：`待录用确认 → 已录用`（唯一终态）。
- **列表列**：复选框、姓名、联系方式、应聘岗位、体检结果、调档函、档案保管单位、录用状态（待录用确认/已录用），操作（详情）。
- **批量/单条操作**：
  - 批量/单条：录用确认、生成调档函、汇总表导出、公示发布。
  - 详情内「录用办理」区块：确认体检结果、生成调档函；并显示体检结果、体检确认时间、档案保管单位、调档函状态/编号、录用状态。
- **详情专属区块**：「录用办理」（体检结果、体检确认时间、档案保管单位、调档函状态/编号、录用状态 + 确认体检结果/生成调档函按钮）。
- **影响因素**：
  - **唯一终态**：`已录用` 为终态，不再有退回/不通过常规流转；`不录用` 亦为终态。
  - **前置强约束**：必须体检合格且校级审核「拟录取」后方可录用确认；体检未确认时「确认体检结果」按钮先行。
  - **后续人事动作**：录用确认后触发调档函生成、档案保管单位登记、公示发布，并同步至招聘网站公示与人事后续环节（入校手续等）。
  - **数据来源**：体检结果、调档函状态/编号来自前序体检与录用办理区块，列表直接展示，不重复录入。

## 6. 跨环节通用影响因素（汇总）

| 影响因素 | 作用范围 | 具体说明 |
|---|---|---|
| **① 招聘种类决定节点序列** | 全局 | `选聘`/`先笔后面`/`先面后笔` 各自对应不同的 `PROCESS_NODES_BY_TYPE` 流程链；左侧树种类列表由所选计划决定，切换计划时树动态重建。 |
| **② 高层次人才计划注入「部门初试」** | 特定计划 | 计划名称含「高层次人才」时，`processStagesFor` 在「面试」后自动插入「部门初试」节点（状态签 `待填写意见→待提交复核→已提交复核→已锁定`），并支持部门初试成绩录入与按岗位排名。该节点目前未写死在 `PROCESS_NODES_BY_TYPE`，属动态注入。 |
| **③ 选聘重映射节点名称** | 选聘种类 | 同一通用环节在选聘下以不同名称呈现：资格审查→资格审查（学院）、笔试→名单确认（人事处）、综合素质考察→学院面试、面试→委员会评议、资格复审→校级面试。需求与实现须保证「同名环节不同显示」的一致性。 |
| **④ 成绩/确认驱动状态转移** | 考试型 | 确认参加→发放准考证→录成绩→（合并成绩视图）通过并下一位/不通过；确认不参加即终止。成绩按准考证号唯一匹配。 |
| **⑤ AI 预审辅助** | 资格审查型 | 列表显式 AI 预审/AI 建议列；AI 仅辅助，最终须人工确认，命中不自动通过。 |
| **⑥ 字段按类型可配置** | 列表列 | 每个环节可单独配置表格字段（`FIELD_DEFS` 按类型分组字段池，同类型环节可跨环节借用字段），配置刷新后保留；结构性状态列（确认状态/准考证号/状态标签）不被字段配置覆盖。 |
| **⑦ 状态已变化并发保护** | 全局 | 记录被他人办理或状态不再允许当前操作时，终止提交并提示最新状态，刷新列表，不覆盖他人已完成结果。终态集合：`已录用/不录用/不通过/放弃/已放弃`。 |
| **⑧ 体检/心理测试接入缺口** | ④体检/⑤心理测试 | 两节点已定义状态与操作但未接入任何招聘种类流程链，左侧树不会出现；实现须补入流程链。 |
| **⑨ 类型归类一致性** | 名单确认/委员会评议 | 需求按用户 4 类归类（归③），原型 `typeOfStage` 暂归「资格审查/考试」，实现须统一字段池与操作形态。 |

## 7. 查询区、导入导出与通用交互规则

### 7.1 查询区（多条件按「且」组合；未填条件不参与过滤；重置恢复默认）
| 字段 | 控件 | 说明 | 必填/默认 |
|---|---|---|---|
| 招聘种类 | 下拉单选 | 全部/选聘/先笔后面/先面后笔/高层次人才等（由当前计划决定） | 非必填，默认「全部」 |
| 岗位 | 输入框 | 岗位名称模糊匹配 | 非必填 |
| AI 预审 | 下拉单选 | 仅资格审查类节点显示；符合/不符合 | 非必填 |
| 高级筛选 | 展开按钮 | 姓名、学历、第一学历、年龄等 | 非必填 |
| 重置 / 查询 | 按钮 | 清空条件 / 执行组合查询 | — |

### 7.2 导入与导出
- **导入成绩/结果**：考试型节点上传 Excel/CSV，按准考证号唯一匹配并自动录入；匹配失败行明确提示，支持下载失败清单。
- **导出**：导出当前列表；选中时导出所选、未选中导出全部；字段至少含姓名、联系方式、应聘岗位、招聘种类、当前状态、办理结果。

### 7.3 通用交互规则
- **加载态**：查询/批量/导入/导出/发送消息时显示加载态并禁重复提交；完成后保持筛选与树选中。
- **空数据**：结果为空展示「暂无数据」+「清空筛选」入口，不显示虚构记录。
- **校验失败**：提交前在字段附近显示原因并定位首个错误字段。
- **服务失败**：保留已填内容，提示可理解原因与重试方式；不暴露技术堆栈。
- **状态已变化**：见 §6-⑦，终止提交并刷新。
- **超时预警**：左侧树叶子人数徽标支持红色高亮，提示存在即将/已超时待办。

## 8. 待确认/待实现缺口清单（供落地前对齐）
1. **体检、心理测试**未接入 3 种招聘种类的 `PROCESS_NODES_BY_TYPE` 流程链 → 需补入（建议位置：校级审核之后、招聘录用之前）。
2. **部门初试**仅由高层次人才计划动态注入，未固化在种类序列中 → 确认是否所有高层次人才计划都需，及是否纳入其他计划。
3. **名单确认（人事处）、委员会评议**的需求归类（③常规审核）与原型 `typeOfStage`（资格审查/考试）不一致 → 实现前统一字段池与操作形态。
4. **心理测试不合格**是否影响录用、是否终止流程 → 需求待拍板（当前与体检「不合格即终止」区分）。
5. **选聘重映射**下「名单确认（人事处）」对应通用「笔试」节点，但两者形态差异大（审核 vs 考试），需确认映射与数据字段对齐方式。
