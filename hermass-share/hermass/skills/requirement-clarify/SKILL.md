# 交互式需求澄清（Step 1 增强：先聊清楚，再生成）

> 仅在缺少会影响结果的业务信息时触发。用户已要求生成且需求明确时直接执行；不因本技能要求重复批准已有授权。
> 目录基准：UI Demo = `${UI_DEMO_ROOT}`；字段单源 = `${ONTOLOGY_ROOT}`。

## 提问纪律

1. **只问关键缺口**：优先一次问一个最关键问题，已有信息不重复问；模板的间距、颜色、行高不交给用户重新选择。
2. **带选项提问**：能枚举的给候选（如"这个按钮是跳转还是弹窗？"），并优先从既有页面找参照（"参考 monitor 页那种筛选区吗？"）。
3. **字段先查再问**：涉及字段时先跑 `node "${UI_DEMO_ROOT}/scripts/find-standard-field.mjs" <名称>`，标准库有就直接提议（"用标准字段『学历』可以吗？"），没有再问用户口径并准备登记扩展。
4. **每轮小结**：每轮结束用 2-3 行复述已达成的共识，再进入下一轮。
5. **模糊不猜**：用户没说的细节一律进 `research.openQuestions`，不自行补全成"确定需求"。

## 提问清单（按区块推进，不要求每页全有）

### 第 1 轮：目标与归属

- 页面目标：解决什么问题、给谁用（角色）、最高频的操作是什么？
- 用户期望：有没有参考截图/参考页面/参考系统？
- 菜单归属：所属产品与角色、菜单名称、功能 key（进 `${UI_DEMO_ROOT}/demos/<产品>/menus/` 注册到 WiseMenuRegistry）。

### 第 2 轮：模板与页面骨架

- 页面核心形态：增删改查列表 / 只读台账 / 卡片流 / 审核流水 / 仪表盘 / 编辑表单 / 导入向导 / 其他？
- 先从 `${UI_DEMO_ROOT}/scenarios/README.md`、`${UI_DEMO_ROOT}/scenarios/scenario-templates-index.html` 及 `template-and-component` 技能的映射表中选择最接近的现有场景页；再读 `${UI_DEMO_ROOT}/specs/page-template-catalog.json` + `${UI_DEMO_ROOT}/templates/` 核对对应组件与装配约束。用户已指定则使用指定页；未指定时需求卡记录首选场景页路径、catalog ID/组件和匹配理由。模板选定后锁定视觉，只确认业务字段和操作，不自行调整间距、配色、布局。无匹配时再选 catalog 组件模板并注明缺口。
- 页面附加结构：要不要树（左树右表？树的数据和层级）、顶部页签、抽屉详情、弹窗、步骤条？

### 第 3 轮：筛选区与工具栏

- 筛选区字段：逐个确认字段名、控件类型（输入/下拉/日期区间/级联）、默认值、是否常用；
- 工具栏按钮：逐个确认名称、功能（新增/导出/批量操作…）、主次（主色蓝只给主按钮）。

### 第 4 轮：表格与操作区

- 表格列：字段清单（回溯 ontology，给 fieldRef）、列宽要点、状态枚举与语义色（六色：灰/蓝/绿/橙/红/青）、默认排序；
- 操作区：行内操作（查看/编辑/删除…）、批量操作、操作列冻结需求；
- 分页与数据量级。

### 第 5 轮：联动与跳转

- 点击行/单元格去哪（跳页面用 `WiseMenuRegistry.route('菜单ID:功能key')`）；
- 跨页跳转、详情页归属、导出内容范围。

## 产出物：结构化需求卡

```markdown
## 需求卡：<页面名>
- **目标**：…
- **用户期望**：…（参考页面：…）
- **菜单**：产品/角色/菜单名称/功能 key
- **模板**：<场景页路径 + catalog 模板 ID/组件 + 匹配理由>；无匹配则记录缺口，选定后保持模板结构与视觉
- **筛选区**：字段×控件类型×默认值
- **工具栏按钮**：名称×功能×主次
- **表格**：列清单（fieldRef）/ 状态枚举与语义色 / 排序 / 分页
- **操作区**：行内操作 / 批量操作 / 冻结
- **树结构**：数据源 / 层级 / 联动（无则写"无"）
- **其他页面细节**：抽屉/弹窗/页签/跳转…
- **openQuestions**：未确认项，标注"需与用户确认"
```

## 确认门（铁律）

1. 需求卡记录已确认内容和缺口，需求清楚且用户已授权生成时直接执行；
2. 必須确认的业务缺口未解决时暂停相关部分，可继续独立检查；
3. 用户补充或纠正需求直接纳入已有任务，不重复确认已明确的内容。
